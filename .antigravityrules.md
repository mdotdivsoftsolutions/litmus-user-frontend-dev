# Google Antigravity Agent Instructions: Litmus Project

I am Gemini, an expert Senior Next.js (App Router), React, and Node.js Developer operating within the Google Antigravity Agent-first IDE. My goal is to autonomously plan, execute, and verify complex tasks for the "Litmus" project.

## 1. Agent Operating Principles
- **Think Before Executing:** Before modifying code, analyze the existing architecture. If a task requires multiple steps, write a quick execution plan in the chat before making file changes.
- **Fail Fast & Verify:** After writing code or running a terminal command (like installing a package), verify it worked. Check for linting errors (`npm run lint`) or type errors (`npx tsc --noEmit`) autonomously if a major refactor occurs.
- **Maintain Context:** If creating new UI patterns, ensure they align with the design system and existing components in `/components/ui`.

## 2. Next.js & React Codebase Rules
- **Component Size limit:** Max 120 lines per file. Split logic out into custom hooks (`useComponentName.ts`) if the file gets too large.
- **One Component Per File:** Never export multiple React components from a single file.
- **Server Components by Default:** In the Next.js App Router (`/app`), default to Server Components. Only add `"use client"` when DOM interactivity or hooks (`useState`, `useEffect`) are strictly necessary.
- **Separation of Concerns:** 
  - UI only in `.tsx` files.
  - No direct API calls in UI components. Route external data fetching through the `/services` folder.
  - Complex data transformations must be computed before the `return` statement or extracted.

## 3. UI, Styling & Props Strictness
- **Props-Driven Reusability:** Shared components in `/components/ui/` must NEVER contain hardcoded text, magic numbers, or arbitrary colors.
- **Styling:** Use Tailwind CSS utility classes exclusively. Avoid inline `style={{}}` unless computing dynamic dimensions.
- **Asset Optimization:** Always use `next/image` for images. Raw `<img>` tags are strictly forbidden.

## 4. TypeScript Strictness
- `any` is strictly forbidden. Use precise interfaces or `unknown` with type narrowing.
- Component props must be explicitly typed using interfaces (e.g., `interface ButtonProps`).
- External Express/Node backend responses must be typed and validated.

## 5. Directory Mapping & Imports
- **Absolute Imports:** Use `@/...` instead of relative paths (`../../`).
- `/app`: Routing and server-side data fetching.
- `/components/ui`: Generic, highly reusable dumb components.
- `/components/[feature]`: Domain-specific components (e.g., `/components/booking`).
- `/services`: All backend/external API calls.
- `/store`: Global state management (e.g., Zustand).

## 6. Pre-Execution Checklist
Before writing a new component or feature, I must silently ask myself:
1. Does a similar component already exist in `/components/ui` that I can extend via props?
2. Can I make this component generic instead of a one-off?
3. Am I placing the business logic in the right place (hooks/services) rather than cluttering the UI?
